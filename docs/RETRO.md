# 复盘：剪辑辅助 Agent（V1.0）

> 这份复盘写给面试官，也写给未来的自己。原则：**所有缺口都写明，不包装**——产品反思能力本身是作品集的一部分。

一句话概括：**把我在客服行业验证过的「AI 承担重复劳动、人保留判断权」方法论，迁移到剪映创作工具场景的一次完整产品实践**——从 SDD、可运行原型，到评测体系与已知缺口。

---

## 1. 主线故事：同一套方法论，两个行业

14 年客服运营经验里，我主导过智能客服从规则引擎到大模型的升级（解决率 60%→80%，转人工率 70%→40%，人力成本 −50%）。那套产品的核心不是"AI 多强"，而是一条人机分工原则：

> **AI 处理高频、规则明确的部分；判断权、最终控制权永远留在人手里。**

做剪辑辅助 Agent 时，这条原则原样迁移了过来：

| 客服项目（已验证） | 剪辑项目（本次实践） |
|---|---|
| AI 预筛 + 人工专席复核 | AI 执行 + 预览快照 + 人工确认 |
| 三级转人工策略（情绪升级/意图漂移/跨业务线） | 主观创意类指令拒绝全自动（叙事/情绪剪辑/创意转场） |
| Badcase 归因按周反哺模型 | 埋点采纳率/二次修改率反哺 Skill 迭代 |
| 「解决率」口径与算法团队统一，防指标虚高 | 「采纳率」定义为用户确认应用才算，重跑记二次修改 |
| 失败降级：AI 不可用时转人工 | 无本地模型时规则路由兜底，纯本地可跑 |

**我不相信"全自动"，我相信"可撤销的半自动"。** 这句话贯穿两份作品。

## 2. JD 三条职责 ↔ 项目设计映射

目标岗位：字节跳动「AI 工具产品经理（多轨道）」，剪映 PC 方向。

| JD 职责 | 项目对应设计 | 证据 | 面试风险与话术 |
|---|---|---|---|
| ① 剪映 PC 工具能力建设：能力丰富度、易用性、创作效率 | 5 个原子 Skill + 预览确认/人工干预交互 | `clip_agent/skills/`（S001–S005）；`clip_agent/preview/` | 风险：这是外部辅助工具，不是剪映内建能力。话术：**先以独立工具验证 Skill 的粒度与采纳率，跑通后再走官方内建化路径**——这正是 JD 第 2 条"探索和交付新解决方案"的验证阶段 |
| ② 用 AI 模型替代传统工具或标准化流程、创建 Agent Skill | 意图解析路由 + Skill 调度引擎 + 人机边界约束 + 失败终止保留 | `clip_agent/core/intent.py`、`scheduler.py`；SDD 第 6 节 | 风险：无真实创作者需求研究数据。见第 6 章缺口 1，有验证计划 |
| ③ 推进预设、Skill 知识沉淀与分发，完善创作者生态 | 创作资产库：调色预设/组合方案/版本回滚/收藏 | `clip_agent/assets/library.py`；`data/assets.json` | 风险：只有"沉淀"（本地单机），没有"分发"（生态链路）。见缺口 2，V1.1 设计已成型 |

## 3. 竞品定位：不做第 N 个单点 AI 功能

（信息截至 2026-10，来源见文末）

- **剪映 PC 现状**（v11.5，2026-09）：AI 能力全部是**单点功能**——智能字幕、AI 文字成片、AI 配音、AI 音乐、画质提升。官方 FAQ 明确「智能粗剪仅是提效起稿，仍需精修」。**没有"可编排、可复用的 Agent Skill"产品形态**——这正是这个 JD 设岗的空白区，与本项目定位一致；官方口径也直接背书了人机边界设计。
- **Adobe Premiere AI Assistant（Beta，2026-07）**：最直接的同构对标——自然语言组装初剪、操作进入撤销历史、权限分「始终询问/自动批准」、显示推理过程。说明「预览确认 + 人工干预」是行业头部共识，不是拍脑袋。
- **DaVinci Resolve 20**：IntelliScript（脚本→粗剪）、AI Music Editor（音乐随片长重排）等，全是单点工具——**没有编排层**，这正是 Skill 调度引擎的差异化。
- **CapCut 模板生态**（创作者计划、导出分成/单模板付费/会员变现）：资产库 V1.1「分享分发」的对标形态，证明"预设/Skill 资产化"有成熟商业路径。

结论：本项目的定位是**剪映生态的"可编排 Skill 层"**——不是又一个 AI 功能，而是让已有的单点能力可以被组合、复用、沉淀。

## 4. 关键产品决策复盘（为什么这么设计）

**D1｜为什么只做 5 个 Skill？**
判据是三条：规则明确、结果可验证、出错修改成本低。每个 Skill 对应创作者高频重复劳动（静音裁切、字幕校对、高光筛选、BGM 对齐、调色套用）。主观创意类（叙事、情绪、转场）明确不做——这是边界，不是能力不足的借口。

**D2｜为什么所有输出必须预览确认？**
信任成本决定采纳率。AI 直接改工程，错了要用户回滚；预览快照先行，错了用户直接放弃，原素材零风险。对标 Premiere AI Assistant 的「始终询问/自动批准」权限设计——行业验证过的做法。客服项目里「人工专席复核」也是同一逻辑。

**D3｜为什么规则路由兜底，而不是纯大模型？**
三个理由：素材隐私（不离开本地）、成本、可演示性（面试现场没装 Ollama 也必须能跑）。LLM 是增强，不是依赖——这是刻意的降级设计，不是技术妥协。

**D4｜为什么单 Skill 失败就终止，而不是继续跑完？**
失败即终止能保证错误可归因（错在哪个 Skill、什么参数），且已完成的步骤结果保留，用户可调参重试。继续执行会让后续结果建立在错误输入上，用户还得逐个排查。

**D5｜为什么输出"时间戳方案"而不是直接改剪映工程？**
剪映 PC 无开放 API，这是现实约束。选择对用户零风险的交付形态：静音段/高光片段时间戳 + ffmpeg 可渲染成片 + 剪映调节面板参数映射（手动导入）。V1.2 视剪映开放能力再评估——**先交付能用的，不等完美的集成**。

**D6｜指标口径怎么防虚高？**
借鉴客服行业"解决率"口径的教训：算法侧自动认为解决≠用户认为解决。剪辑项目里：采纳率 = 用户确认应用 ÷ 全部决策；修改参数重跑计"二次修改"不计采纳；非交互预览单独记录，不混入放弃率（本次复盘已修复，见第 7 章）。**口径先对齐，数据才有意义。**

## 5. 指标设计（对齐 SDD 第 6 章）

| 类别 | 指标 | 现状 |
|---|---|---|
| 效率 | Skill 平均执行耗时、操作步骤减少量 | 耗时已埋点；步骤减少量需对照实验（见缺口 4） |
| 质量 | 结果采纳率、二次修改率、报错失败率 | 已实现埋点与报表；数值来自演示数据 |
| 生态 | 资产保存率、复用率、分享率 | 保存/复用/收藏已埋点；分享率 V1.1 才可测 |

## 6. 缺口分析与验证计划（面试主战场）

**Gap 1｜没有真实创作者需求研究**
现状：Skill 清单来自我的场景推演，不是访谈数据。
已补：案头研究（公开创作者痛点证据汇总）见 `docs/USER-RESEARCH.md`——用于形成需求假设，**不能替代访谈验证**（公开吐槽 ≠ 付费意愿 ≠ 优先级）。
验证计划：5–8 位创作者种子测试（口播/剧情/生活三类各 2–3 人）。访谈问题：剪一条视频最烦的三个步骤是什么？标准化工具你会信任到什么程度？成功标准：目标 Skill 采纳率 ≥60%，平均二次修改 ≤1 次；不达标就砍 Skill 或改参数默认值。
话术：「这个版本验证的是流程和粒度，不是需求。案头研究给了假设，下一步是 5–8 人的种子测试。」

**Gap 2｜分发/生态缺失**
现状：资产库是本地单机版本，没有分享、榜单、收益链路。
已补规划：`docs/ECOSYSTEM-PLAN.md`——三阶段路径（沉淀 → 流通 → 激励）、质量治理、冷启动与指标设计。
话术：先验证"资产有人用"，再谈"生态有收益"。

**Gap 3｜行业经验缺口（客服→创作工具）**
这是面试必问的「为什么从客服跳到剪映」。
话术：第 1 章的迁移论证（人机分工方法论 + 指标口径经验 + 降级设计），加上主动学习动作（跟踪剪映版本迭代、泡创作者社区、自己用剪映剪素材做 demo）。**不回避行业经验空白，强调方法论的稀缺组合。**

**Gap 4｜性能/效率指标无基线**
现状：报表只有绝对耗时，没有"手动 vs Agent"对照。
验证计划：同一条素材做 A/B 对照（手动剪 vs Agent 辅助），记录完成时间与操作步数。成功标准：标准化环节耗时减少 ≥40%。

**Gap 5｜高光筛选是启发式，不是内容理解**
现状：切变密度 + 瞬时响度的加权评分，不是多模态语义精排。
话术：V1 用可解释的启发式先验证"筛选这个交互值得做"；V1.1 接多模态模型做语义精排（"这条是教程类还是搞笑类"）。诚实标注准确率上限。

## 7. 真缺陷修复记录 + 待修 Backlog

**已修复（本次复盘）：**
- **S003 过短镜头合并逻辑错误**：原实现按"距已合并片段起点的距离"判断，导致离起点远的短镜头被漏合（且长片段会误吞后续镜头）；改为按当前镜头自身时长判断，并补 4 条回归测试。
- **非交互模式默认记"放弃"**：污染放弃率指标。改为记录独立状态 `previewed`（仅预览），不计入采纳/放弃统计。
- **资产"复用"埋点误触发**：原实现只要传了 `--asset` 就计数；改为仅当 S005 实际成功使用预设时计入。
- **交互模式此前从未实测**：本次用伪终端验证了完整决策流程（应用 / 放弃路径均验证通过）。

**待修 Backlog（不影响演示）：**
- 交互模式"修改参数重跑"输入未知参数时静默忽略，应提示可用参数名；
- S002 折行未强制两行上限（超长句会出 3–4 行）；
- 长视频渲染无实时进度（ffmpeg 子进程输出未流式解析）；
- 单次单任务，无并发/队列（演示够用，产品化需要）。

## 9. 面试 Q&A 预演（12 题）

1. **这个产品和剪映是什么关系？为什么不做插件？**
   独立辅助工具。剪映 PC 无开放 API，插件不可行；输出时间戳方案 + 剪映可直接导入的 SRT + 调节面板参数映射。V1.2 视开放能力评估集成。

2. **目标用户是谁？为什么先做他们？**
   短视频创作者（口播/剧情/生活类）。口播类对静音裁切/字幕校对需求最刚性、规则最明确——**先做规则明确的人群，验证 Agent 采纳率，再扩场景**。

3. **AI 一键生成工具如何平衡自动化效率与个性化创意？**（面经高频原题）
   用 Skill 粒度切分：规则明确的标准化动作交给 AI；主观创意（叙事/情绪/转场）拒绝全自动，只做辅助推荐。预览确认制保证创作者永远有最终控制权。输出是"可撤销的半自动"，不是"一键成片"。

4. **为什么用户要预览确认，不能全自动？**
   信任成本与纠错成本。AI 误改工程的回滚成本远高于预览确认的成本；行业对标 Premiere AI Assistant 的「始终询问/自动批准」权限设计。客服项目的「人工复核」是同一原则。

5. **指标怎么定义的？验证过吗？**
   采纳率/二次修改率/报错率，口径防虚高（借鉴客服"解决率"口径统一经验）。目前是设计+演示数据，真实验证计划见 RETRO 缺口 1（5–8 人种子测试）。**不假装验证过。**

6. **Agent 的 Function Calling 可接受失败率是多少？**（面经高频）
   单 Skill 失败即终止、保留已完成结果、错误可归因——失败不会级联。目标失败率需真实数据支撑，V1 不给拍脑袋的数字；设计上通过参数可调 + Badcase 清单迭代逼近（与客服 Badcase 归因同法）。

7. **为什么用规则路由兜底，而不是纯大模型？**
   隐私（素材不出本地）、成本、可演示性。LLM 是增强不是依赖——演示环境没装模型也能完整跑通。

8. **怎么防止 AI 破坏用户工程？**
   三层：原素材只读（渲染输出新文件）；预览快照先行；放弃即零修改。失败也不会动原文件。

9. **竞品你怎么看？**
   见第 3 章：剪映 PC 全单点无编排层；Premiere AI Assistant 是同构对标；DaVinci 单点工具；CapCut 模板生态是分发对标。定位是"可编排 Skill 层"。

10. **生态/分发怎么做？**
    资产库现状（沉淀/版本/收藏）+ V1.1 分享/榜单/变现阶段设计，对标 CapCut 模板创作者计划。先验证"有人用"再做"有收益"。

11. **如果给你 6 个月，路线图怎么排？**
    见第 10 章：先用户验证（M1），再分发（M2），再多模态（M3），最后评估剪映集成（M4）。

12. **你这个项目最大的失败/重来一次怎么做？**
    诚实版：我第一版 SDD 是先写设计后想验证——重来会先做 5 个创作者访谈再定 Skill 清单。这个教训来自客服行业：当年"解决率"口径也是先被指标虚高坑过才统一。**先定义测量，再动手设计。**
